## 📅 주간 PR & 리뷰 사이클

| 구분 | 월 | 화 | 수 | 목 | 금 | 토 | 일 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **팀원 (쿠키즈)** | `feature/*` 브랜치에서 기능 개발 | `feature/*` 브랜치에서 기능 개발 | **[팀장]** `develop` → `main` PR 요청<br>*(18:00 전까지)* | `develop`에서 `refactor/*` 브랜치 생성 후 피드백 반영 | `develop`에서 `refactor/*` 브랜치 생성 후 피드백 반영 | **[팀장]** 수요일 PR에 대한 재리뷰 요청<br>*(10:00 전까지)* | 멘토 Approve 후 `develop` → `main` 머지<br>*(23:59 전까지)* |
| **멘토** | | | **1차 리뷰 진행**<br>*(목 22:00까지 완료)* | | | **2차 재리뷰 진행** | **최종 Approve 완료**<br>*(일 10:00까지)* |

* 코드 리뷰는 팀원끼리 상시 진행하며, 멘토님과의 코드 리뷰는 주차별 `develop` 브랜치에서 `main` 브랜치로 올라오는 PR을 담당 멘토님이 확인 후 피드백하는 프로세스로 진행합니다.
* 코드 리뷰는 팀 내부에서 수시로, 그리고 멘토님에게는 매주 정해진 일정에 따라 요청합니다.
* 변경사항이 발생할 시, 같은 도메인을 담당하는 그룹 팀원의 상호 리뷰를 받습니다. (최소 같은 그룹 팀원 1인이상 리뷰 받기)
* 팀 기준과 일정을 지키는 것이 중요합니다.

## 🌿 브랜치 전략

```text
main                        # [보호] Rulesets 적용, 직접 push 금지, PR merge만 허용
  ↑ (수요일/토요일 PR)         # 멘토 코드리뷰 진행, Approve 완료 시 main으로 머지
develop                     # [기본 브랜치] 팀에서 자유롭게 관리/사용 (보호 X, 핫픽스/간단 리팩토링 직접 push 가능)
  ↑ (기능별 PR)               # feature/* → develop (팀 내 상호 리뷰 후 머지)
  ↑ (핫픽스/리팩토링 PR)        # refactor/* → develop (멘토 피드백 반영)
feature/<이슈명>              # 각자 기능 단위 브랜치
refactor/<내용>              # 멘토님 피드백 반영용 브랜치 (develop에서 생성)
```

- **`main`**: Rulesets로 보호. 직접 `push` 금지, PR `merge`만 허용.
- **`develop`**: 보호하지 않음. 직접 `push`/`merge` 자유 (핫픽스, 간단 리팩토링 등).

## 🔁 코드 리뷰 워크플로우

> 코드 리뷰는 일주일에 1회, 총 9회 진행합니다. *(4주차 테크스펙 리뷰 제외)*

### 1. 팀원 간 리뷰 (상시 진행)
- 모든 기능/버그/리팩토링 작업 후, 변경사항은 Pull Request(PR)로 공유하고 팀원 리뷰를 받습니다.
- 팀원은 각자 `feature/*` 브랜치에서 기능 단위로 작업합니다.
- `develop` ← `feature/*` PR 생성 후, 팀 내 리뷰를 거쳐 머지합니다.
- **PR 본문 필수 기재 사항:**
    1. 구현한 기능 내용 요약
    2. 리뷰받고 싶은 포인트
    3. 고려한 설계/예외 상황
- 팀 내 리뷰 세부 규칙은 팀별로 자유롭게 설정합니다.
- 핫픽스나 간단한 리팩토링은 `develop`에 직접 `push`하여 빠르게 수정합니다.
- 팀원들은 성실한 리뷰 댓글과 approve/반려 의견을 남기고, 필요한 경우 Peer Review도 진행합니다.

### 2. 멘토님 리뷰 프로세스
- 매주 **수요일 18:00까지** 1차 PR(리뷰 요청), **토요일 10:00까지** 2차 재리뷰 요청을 팀장(PM)이 작성하여 제출합니다.
- 팀장이 `develop`에서 `main`으로 PR을 생성합니다.
- PR 본문에 이번 주 변경사항 요약 및 리뷰받고 싶은 코드/설계 포인트를 명확히 강조합니다.
- 멘토님 Approve 후 팀장이 머지합니다.
- 완벽하게 리팩토링되지 않더라도 수용 가능한 피드백은 넘어가고, 수용 불가능한 이슈는 최대한 빠르게 처리하여 **일요일 23:59까지** `main`에 머지할 수 있도록 Approve를 진행합니다.

#### ⏰ 상세 일정표
| 요일 / 시간 | 담당자 | 활동 내용 |
| :--- | :--- | :--- |
| **수 18:00 까지** | 팀장 (PM) | **1차 PR** (리뷰 요청) |
| **목 22:00 까지** | 멘토님 | **1차 리뷰** 완료 |
| **토 10:00 까지** | 팀장 (PM) | **2차 PR** (재리뷰 요청) |
| **일 10:00 까지** | 멘토님 | **2차 리뷰** 진행 + 최종 Approve |
| **일 23:59 까지** | 팀장 (PM) | 멘토님 Approve 확인 후 `main`으로 최종 머지 |

### 3. 피드백 반영
- 멘토님 피드백 후 개선사항은 `develop`에서 `refactor/*` 브랜치를 생성하여 반영합니다.
- `refactor/*` 브랜치 PR은 팀 내 리뷰 후 `develop`에 머지하며, PR 링크를 멘토 리뷰 댓글에 답글로 남겨 공유합니다.
- 피드백은 무조건 수용하기보다 팀 내에서 충분히 논의하여 의견을 조율하고 반영합니다.
- `refactor/*` 브랜치 작업과 신규 기능 개발(`feature/*`) 작업을 병행할 경우, `develop` 머지 시 충돌(Conflict)이 발생하지 않도록 유의합니다.

## 💬 리뷰 커뮤니케이션 팁 & 팀 내 규칙

### 커뮤니케이션 팁
- 피드백을 단순히 수용하기보다는, 왜 그렇게 생각하는지 묻고 토론해 보세요.
- 코멘트가 마음에 들지 않더라도, 감정을 배제하고 기술적으로 응답하는 연습을 해보세요.
- 정답을 찾는 것이 목적이 아니라, 더 나은 방향을 함께 고민하는 것이 코드 리뷰의 핵심입니다.

### 팀원 간 리뷰 규칙 권장 예시
- `feature` → `develop` PR은 작고 자주 올릴 것 (기능 단위 분할)
- 최소 1명 이상의 팀원 리뷰 후 머지
- 리뷰 기한은 PR 생성 후 24시간 이내
- 질문 및 리뷰 포인트는 구체적으로 작성
- 단순 Approve 지양, 구체적인 피드백/코멘트 1개 이상 남기기

## 📝 PR 작성 가이드

> 정해진 템플릿은 없습니다. 팀마다 만드는 제품과 개발 방식이 다르므로 형식을 강제하지 않습니다.  
> **핵심 목적은 리뷰어가 "무엇을 봐야 하는지" 명확히 알 수 있도록 작성하는 것입니다.**

### 1. 멘토 대상 PR 작성법
- **수요일 18:00 1차 리뷰 요청:**
    - 월~화에 작업한 신규 내용
    - 지난주 수~일 동안 작업하여 새로 `develop`에 머지된 신규 feature
- **토요일 10:00 2차 재리뷰 요청:**
    - `refactor` → `develop`으로 보낸 PR 링크 삽입
    - 즉, 멘토의 피드백을 반영하여 develop 에 머지된 수정 내역을 삽입합니다.
    - 신규 feature/* 에서 작업한 내용이 혼재되지 않도록 반드시 유의해주세요.

### 2. 모든 PR에 반드시 담아야 할 3가지
1. **변경 요약**
    - 단순 커밋 목록 나열이 아닌, "무엇을, 왜" 작업했는지 2~3문장으로 요약
    - *예시: "주문 취소 API를 추가했습니다. 기존 주문 수정 로직과 상태 전이가 겹쳐서 상태 관리를 별도 클래스로 분리했습니다."*
2. **리뷰 포인트**
    - 파일, 함수, 설계 결정 지점을 명확히 지정 ("전체 검토해주세요" 금지)
    - *예시: "OrderStateMachine의 상태 전이 정의에 누락된 케이스가 없는지 / 트랜잭션 경계를 서비스 레이어에 둔 결정이 적절한지 검토 부탁드립니다."*
3. **설계 및 예외 고려사항**
    - 다른 대안 대신 현재 방식을 선택한 이유 기술
    - 인지하고 있으나 의도적으로 처리하지 않은 예외/한계점 솔직하게 공유
    - *이 항목을 통해 단순 "코드 지적"을 "설계 토론"으로 발전시킬 수 있습니다.*

## ⚖️ PR 유형별 비교

| 구분 | `develop` ← `feature/*` / `refactor/*`<br>*(팀 내 리뷰)* | `main` ← `develop`<br>*(멘토 리뷰)* |
| :--- |:-----------------------------------------------------|:--------------------------------|
| **범위** | 기능 하나                                                | 이번 주 작업 전체                      |
| **요약** | 이 기능이 하는 일                                           | 이번 주 무엇이 얼마나 진척됐는지              |
| **리뷰 포인트** | 구현 디테일 (네이밍, 예외 처리, 테스트 코드 등)                        | 설계설계·구조 (레이어 분리, 확장성, 기술 선택)    |
| **분량** | 짧아도 됨                                                | 맥락을 충분히 하기                      |

## ⚠️ 피해야 할 PR 유형
- ❌ 제목이 "주간 작업"이고 본문이 비어 있는 PR
- ❌ 커밋 50개가 한 번에 올라온 PR (기능 단위로 분할 필요)
- ❌ 본문이 "리뷰 부탁드립니다" 한 줄인 PR
- ❌ 어디까지가 완료된 작업이고 어디부터가 진행 중인지 불명확한 PR
