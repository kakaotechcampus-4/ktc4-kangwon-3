# 진단 세션 보관·복원·종료

진단 세션은 메모리(`sessions/store.py`)에서 관리하며, 재시작 시 복원할 세션만 AI DB에 함께 보관한다.
배포 시 실행 중인 진단은 drain으로 끝까지 실행하고(6장), 시작 전이거나 답변을 기다리는 세션은 이 보관으로 유지한다.

## 1. 개요

- `DATABASE_URL`이 없으면 보관하지 않고 메모리에만 둔다(재시작 시 소멸).
- 세션 설정은 `app/config/session.py`에 있으며, 환경변수로 조정할 수 있는 값과 고정값은 다음과 같다.

| 이름 | 기본값 | 의미 |
|---|---|---|
| `SESSION_RETENTION_SECONDS` | 3600 | 종료(완료·실패) 세션의 메모리 보관 시간(초) |
| `AWAITING_INPUT_RETENTION_SECONDS` | 86400 | 답변 대기 세션 보관 시간(초). 질문을 전송한 시각부터 계산한다 |
| `MAX_RUNNING_SESSIONS` | 10 | 동시 실행 상한. 초과한 세션은 대기한다 |
| `MAX_INFLIGHT_SESSIONS` | 20 | 대기 + 실행 중 세션 상한. 초과하면 접수를 거절한다 |
| `MAX_DEV_INFLIGHT_SESSIONS` | 3 | 샌드박스 진단 대기 + 실행 중 상한(전체 상한에도 포함). `MAX_INFLIGHT_SESSIONS` 이하여야 하며, 초과하면 기동에 실패한다 |
| `MAX_PARALLEL_TOOLS` | 6 | 진단 하나에서 동시에 실행하는 Tool 수. 1이면 순차 실행 |
| `SESSION_MAX_DURATION_SECONDS` (고정) | 600 | 접수부터 결과까지 최대 시간(초). 초과하면 시간 초과 실패 |
| `SESSION_DRAIN_SECONDS` (고정) | 580 | 서버 종료 시 실행 중 세션을 기다리는 최대 시간(초) |
| `SESSION_SWEEP_SECONDS` (고정) | 30 | 시간 초과 실패 처리·보관 시간 경과 세션 삭제 주기(초) |

## 2. 보관 대상

보관 여부는 `sessions/transitions.py`의 `STATUS_TRAITS.archived`(상태별 보관 여부)와 실행 종류로 정한다. 개발용 샌드박스 진단(`run_type=test`)은 상태와 관계없이 보관하지 않으며(`sessions/store.py`), BE 연동 더미(`dummy`)는 운영 진단과 동일하게 보관한다.

| 상태 | 보관 | 재시작 시 |
|---|---|---|
| 접수 (대기, 첫 진단·재진단) | O | 동일한 runId로 다시 실행한다. 이 실행으로 BE에 전송한 콜백이 없으므로 BE는 차이를 알 수 없다. 접수 시각은 유지되므로 서버가 중단된 동안 최대 시간(600초)을 넘겼으면 실행하지 않고 `AI_TIMEOUT`(재시도 가능) 실패 콜백을 전송한다 |
| 실행 중 | O | drain 없이 중단된 실행(메모리 부족·재부팅 등)이다. 다시 실행하지 않고 즉시 `AI_TIMEOUT`(재시도 가능) 실패 콜백을 전송한다 |
| 답변 대기 | O | 그대로 복원하며, 답변이 오면 재진단한다(보관 시간은 질문을 전송한 시각부터 그대로 계산) |
| 완료·실패 | X | 결과 콜백이 이미 전송됨 |
| 개발용(샌드박스) 진단 | X | 콜백이 없는 확인용 |

## 3. 표 `diagnosis_sessions`

| 칸 | 내용 |
|---|---|
| `product_id` (키) | 상품 ID. 상품당 한 행이므로 새 접수·재접수는 덮어씀 |
| `status`, `run_type` | 상태, 실행 종류 |
| `updated_at` | 세션 마지막 변경 시각 |
| `session` (jsonb) | `DiagnosisSession` 전체 (원래 입력, 실행 ID, 질문·답변, 회차, 이전 결과, 접수 시각). 복원은 이 값만으로 수행 |
| `fetched_at` | 마지막으로 저장한 시각 |

- 표는 기동 시 `init_db`가 생성한다(이미 있으면 건너뜀). 다른 표는 [DB_CACHE.md](DB_CACHE.md)를 참고한다.
- 복원 시 현재 세션 형식과 일치하지 않는 행(배포로 형식이 바뀐 이전 행)은 경고를 기록하고 삭제한다.

## 4. 저장·삭제 시점

| 사건 | DB |
|---|---|
| 접수, 실행 시작, 질문으로 종료, 재접수 | 저장 (덮어쓰기) |
| 단계 변경, Tool 진행 | 저장하지 않음 (상태가 그대로이므로 복원에 필요 없음) |
| 완료, 실패 (시간 초과 포함) | 삭제 |
| 답변 대기 보관 시간 경과 | 삭제 (세션 정리 루프) |

- 세션 저장소 잠금 안에서 저장하므로 동일한 세션의 저장·삭제 순서가 뒤바뀌지 않는다.
- DB를 사용할 수 없으면 경고만 기록하고 진단은 메모리에서 계속 실행된다. 실패 뒤 60초 동안은 DB를 건너뛴다(`DbSkip`, 응답 캐시와 별도 상태).
  건너뛴 동안의 변경은 DB에 남지 않으므로 복원 시 이미 끝난 세션이 복원될 수 있으나, BE가 이미 받은 결과·실패로 간주하고 무시한다.

## 5. 기동 순서와 복원 (`app.startup`)

DB 준비(`init_db`) → 세션 관리자·콜백·지표 구독 연결 → 보관된 세션 복원 → 요청 수신 시작 순이다.
구독을 모두 연결한 뒤 복원하므로 복원한 세션의 결과·실패도 콜백으로 전송된다. 복원 시 기록되는 로그 줄은 [AI_LOGGING.md](../observability/AI_LOGGING.md) 4.1절을 참고한다.

## 6. 서버 종료 (drain)

배포·`docker stop` 시 실행 중이던 진단은 끝날 때까지 기다린다. 끝난 결과는 평소와 동일하게 콜백으로 전송된다.

- 대기 시간은 580초(`SESSION_DRAIN_SECONDS`)와 실행 중인 세션이 모두 최대 시간(600초)을 넘기는 시각 중 이른 쪽이다. 최대 시간을 넘긴 세션은 시간 초과 실패 콜백을 전송한다.
- 이후 남은 콜백을 최대 15초 동안 전송하고 종료한다. 컨테이너 종료 대기(`stop_grace_period`)는 600초이다.
- 대기 중 세션은 취소된다. DB에 보관하는 경우 재시작 시 2장의 규칙으로 처리하며, 보관하지 않는 경우 폐기된다. 멈춘 상품은 `서버 종료로 진단을 멈춤`(DB 보관) 또는 `서버 종료로 진단을 버림` 로그 줄로 확인한다.
- 대기하는 동안 새 요청은 받지 않는다. BE는 전달하지 못한 요청을 대기 상태로 되돌린 뒤 다시 전송한다.

## 7. BE 연동

BE 코드를 확인한 결과 재시작 뒤 콜백은 다음과 같이 처리된다.

- 실패 콜백은 BE가 순번(`sequence`)을 확인하지 않고 runId로만 확인한다. 재시작 뒤 순번 1로 전송하여도 반영된다.
- 순번은 진행 콜백의 단계별 순서에만 사용된다. 다시 실행하는 대기 세션은 이 실행으로 전송한 콜백이 없으므로 1부터 시작하여도 문제없다.
- BE의 멈춘 진단 정리(15분)가 먼저 실패 처리한 뒤 늦게 결과가 도착하면, BE는 실패 콜백을 이미 끝난 진단으로 간주하여 무시하고, 결과 콜백은 409(`COMMON-010`)로 거절한다. 발신함은 `COMMON-010`을 재시도 없이 폐기한다(409 중 `COMMON-009`만 재시도).
