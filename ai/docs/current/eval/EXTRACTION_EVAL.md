# 추출 에이전트 평가

추출 에이전트(`app/agents/extraction/`)가 상세페이지를 **일관되게 잘못 해석하는 경우**를 찾기 위한 평가 기준이다. 실행 결과 저장, 측정 조건 기록, 원문 비공개, 평가셋 구분 등 공통 규칙은 [EVAL_COMMON.md](EVAL_COMMON.md)를 참고한다.

## 1. 평가 원칙

- **한 번의 실행으로 채점하지 않는다.** 동일한 입력도 실행마다 다른 값이 나올 수 있으므로 N회 반복하여 안정성을 함께 확인한다.
- **정확도 하나로 판단하지 않는다.** true와 false를 오가는 필드는 정확도가 일부 맞는 것이 아니라 근거가 없다는 신호이다.
- **`null`과 `false`를 동일한 오답으로 세지 않는다.** `false`는 "없음을 확인"하였다는 적극적 주장이고, `null`은 판단 유보이다. 규제 판정에서 두 값의 위험도는 다르다.

## 2. 필드별 판정 기준

22개 필드를 채점 방식이 다른 3군으로 나눈다.

### 2.1 3-state boolean 15개 — 위험도 차등 채점

대상: `electrical_powered` `wireless_comm` `wireless_charging` `wireless_shield`
`battery_included` `battery_is_the_product` `heating` `food_contact` `skin_contact`
`medical_claim` `cosmetic_claim` `weapon_like` `plant_material` `chemical_product` `for_children`

정답(GT)과 예측(P)의 조합 9가지를 **같은 무게로 세지 않는다**(`app/eval/grading.py`).

| GT \ 예측 | `true` | `false` | `null` |
|---|---|---|---|
| **`true`** | 정답 | **C1** | C2 |
| **`false`** | C3 | 정답 | C2 |
| **`null`** | **C1** | **C1** | 정답 |

**C1 (치명) — 규제 판정이 드러나지 않게 틀어진다**
- `GT=true, P=false`: 해당 특성을 "없음"으로 확정하여 심사 Tool이 선택되지 않으며, 규제가 검출되지 않는다.
- `GT=null, P=true/false`: 페이지에 근거가 없는데 확정하므로 하위 에이전트가 그 확정을 신뢰한다.

**C2 (보수적 미탐) — 안전한 실패**
- `P=null`: 정보 부족으로 넘어가며, 하위 단계에서 "확인 필요"로 처리할 수 있다.

**C3 (오탐) — 비용만 드는 실패**
- `GT=false, P=true`: 불필요한 Tool이 실행되지만 판정 자체는 틀리지 않는다.

> C1을 0으로 만드는 것이 1차 목표이다. C2·C3은 감시하되 C1과 바꿀 수 있으면 바꾼다
> (확정할 수 없으면 `null`로 두는 편이 항상 낫다).

**GT를 `null`로 매기는 기준**: 상세페이지 텍스트·이미지에 그 특성을 판단할 **직접 근거가 없을 때**이다.
"케이스이므로 손에 닿을 것이다" 같은 상식 추론은 근거가 아니다. 추론으로 채우기 시작하면
정답 자체가 사람마다 달라져 기준이 무너진다.

### 2.2 자유 텍스트 4개 — 완전 일치로 채점하지 않는다

의미가 같아도 실행마다 표현이 달라지므로 문자열 완전 일치로 채점하지 않는다.

| 필드 | 채점 방식 | 이유 |
|---|---|---|
| `target_age` | **원문 부분 문자열 포함** 여부 | 프롬프트가 원문 보존을 요구한다. `"만 14세 이상"`을 `"14세"`로 줄이면 오답 |
| `product_name` | 정답에 등록한 **필수 키워드 전부 포함** | 제목이 길어 표현이 흔들린다. 핵심 명사만 본다 |
| `category` | **허용 목록 중 하나** | `"방향제"` / `"디퓨저"` 같은 동의어를 미리 등록 |
| `intended_use` | **필수 키워드 포함** | 위와 동일 |

`target_age`만 엄격하게 채점하는 이유는 이 필드의 값 자체가 판정 근거(어린이제품 안전 기준)로 사용되기 때문이다. 나머지는 Tool 선택 참고용이므로 표현의 흔들림을 허용한다.

### 2.3 리스트 3개 — 놓친 것과 지어낸 것을 나누어 센다

| 필드 | 필수(놓치면 오답) | 금지(있으면 오답) | 중점 |
|---|---|---|---|
| `attributes` | 정답에 등록한 **값** 전부 (항목 이름은 보지 않음) | 페이지에 없는 값 | 재현율·정밀도 모두 |
| `conflicts` | 정답에 등록한 모순 전부 | — | **재현율만** |
| `listing_text` | 놓치면 표시·광고 심사가 누락되는 판매자 문구 | 구매자 리뷰·플랫폼 공통 문구 | 모두, **기존 집계와 별도** |

`conflicts`의 오탐은 세지 않는다. 모순은 "확정"이 아니라 "확인이 필요한 후보"이기 때문이다. 오탐의 비용은 사람이 한 줄 더 읽는 것이고, 미탐의 비용은 전기·전지 축의 판정이 통째로 누락되는 것이다.

선택 에이전트는 표시·광고 심사 여부를 정할 때 `listing_text`**만** 확인한다.

- **놓치면 C1이다.** 의심 문구가 누락되면 표시·광고 심사가 통째로 누락된다. `conflicts` 누락이 C1인 이유와 같다. 그러므로 필수에는 누락되면 심사가 누락되는 문구만 등록한다. 제목처럼 누락되어도 심사가 누락되지 않는 문구를 등록하면 C1의 근거가 없다.
- **혼입되면 C3이다.** 구매자 리뷰("효과는 100%입니다")나 플랫폼 문구("문제 발생 시 환불")는 페이지에 있는 문구이므로 지어낸 것(C1)은 아니며, 표시·광고 심사를 불필요하게 실행하게 만든다.
- **혼입된 수는 하한값이다.** 정답표에 등록한 문구가 포함되었는지만 확인하므로, 등록하지 않은 리뷰나 바꾸어 옮긴 리뷰("효과 100%")는 세지 못한다.
- **C1·C2·C3 집계와 합산하지 않는다.** 합산하면 채점 항목이 늘어 분모가 커지고, 수정한 것이 없는데 C1 비율이 내려간 것처럼 보인다. 러너는 `[listing_text]` 줄로 별도 표시한다.
- **반복 실행에서의 혼입 빈도는 회차로 센다.** 항목 수만 보면 한 번 크게 혼입되었는지 매번 조금씩 혼입되었는지 구분할 수 없으므로, 러너가 "섞인 회차 N/회차 수"를 함께 표시한다.
- **가격·할인 표시**("권장 소매자 가격", "88% 할인")는 필수도 금지도 아니다. 플랫폼 화면에 표시되지만 할인율 과장은 표시·광고에서 실제로 문제가 되는 유형이므로 한쪽으로 정하지 않는다.

## 3. 정답표 형식

정답표는 픽스처와 같은 이름으로 `ai/tests/eval_truth/<픽스처 이름>.json`에 둔다. 러너와 테스트가 그대로 읽어 채점한다. 아래는 `power_bank.json`의 발췌이다.

```json
{
  "fixture": "power_bank.txt",
  "reviewed_by": "gityhb",
  "reviewed_at": "2026-09-16",
  "tags": ["기존 실패", "애매"],
  "summary": "제목엔 'MagSafe 1460mAh 케이스', 스펙표엔 '배터리 미포함' + '전자 부품 또는 마더보드 미포함'. 카테고리 표시는 '보조배터리'인데 breadcrumb은 '휴대폰 액세서리'. 배터리·전기 관련 특성을 어느 쪽으로도 확정할 수 없다.",

  "booleans": {
    "battery_included": {
      "value": null,
      "evidence": "제목 'MagSafe 1460mAh 케이스' / 스펙표 '배터리 속성: 배터리 미포함'",
      "why_not_other": "두 표기가 정면으로 충돌한다. true도 false도 확정 근거가 없고 conflicts로 보고해야 한다."
    },
    "plant_material": {
      "value": false,
      "evidence": "스펙표 '본체재질: TPU(열가소성 폴리우레탄)'",
      "why_not_other": "재질이 명시돼 있고 식물성이 아니다."
    },
    "skin_contact": {
      "value": null,
      "evidence": "(피부 접촉 관련 언급 없음)",
      "why_not_other": "'휴대폰 케이스니까 손에 닿는다'는 상식 추론이다. 페이지에 근거가 없다."
    }
  },

  "verbatim": {
    "target_age": { "value": null, "evidence": "(연령 표기 없음)" }
  },

  "keywords": {
    "product_name": { "required": ["케이스"] },
    "category": { "allowed": ["보조배터리", "휴대폰 액세서리", "휴대폰 케이스", "휴대폰&액세서리"] }
  },

  "attributes_required": [
    { "name": "배터리 용량", "value": "1460mAh", "evidence": "제목 'MagSafe 1460mAh 케이스'" }
  ],
  "attributes_forbidden": [
    { "name": "정격전압", "value": "220V", "reason": "페이지에 전압 표기가 전혀 없다" }
  ],
  "conflicts_required": [
    { "must_contain": "1460mAh", "evidence": "용량 표기와 '배터리 미포함'이 같은 페이지에 있어 모순 후보로 보고해야 한다" }
  ]
}
```

| 키 | 내용 |
|---|---|
| `fixture` | 원문 파일 이름(원문 폴더 기준 상대 경로) |
| `reviewed_by`·`reviewed_at`·`tags`·`summary` | 검수자·검수일·분류 태그·요약 |
| `booleans` | 3-state boolean 정답. 필드마다 `value`·`evidence`·`why_not_other` |
| `verbatim` | 원문 부분 문자열로 채점하는 필드 |
| `keywords` | 필수 키워드(`required`) 또는 허용 목록(`allowed`)으로 채점하는 필드 |
| `attributes_required`·`attributes_forbidden` | 반드시 포함되어야 하는 속성 값, 포함이 금지된 속성 값 |
| `conflicts_required` | 보고해야 하는 모순(`must_contain`) |
| `listing_text_required`·`listing_text_forbidden` | `listing_text`에 포함되어야 하는 문구(`must_contain`), 포함이 금지된 문구(`must_not_contain`) |

- 정답표는 채점 전에 스키마와 대조한다(`app/eval/scoring.py`의 `check_truth`). 스키마에 없는 필드이거나 `booleans`에 boolean이 아닌 필드가 있으면 중단한다. 필드 이름 오타는 모델 출력에서 항상 `null`로 읽혀 정답으로 채점되므로, 측정값을 오염시키기 전에 차단한다.
- `attributes`는 **값으로만 대조하고 항목 이름은 보지 않는다.** 같은 값을 실행마다 다른 항목 이름으로 적거나 여러 값을 한 항목에 이어 쓰는 경우가 있으므로, 이름·묶음 차이를 누락으로 세면 사실 포착 여부가 아니라 라벨 표현을 측정하게 된다.
- `evidence`는 **원문 인용**으로 적는다. 요약하면 나중에 원문과 대조할 수 없다.

### `why_not_other`를 필수로 두는 이유

`null`과 `false`를 가르는 판단이 이 평가에서 가장 자주 틀리는 지점이다. 정답을 매긴 사람이 **왜 다른 값이 아닌지**를 남기지 않으면 다음 문제가 생긴다.

- 다른 사람이 그 정답에 동의하는지 검증할 수 없다.
- 모델이 틀렸을 때 프롬프트를 어떻게 수정할지 단서가 없다.
- 정답 자체가 틀렸을 가능성을 걸러낼 수 없다.

## 4. 정답표 구성

- 정답표는 `tests/eval_truth/`에 있으며, `tags`로 상품의 성격을 구분한다.

| 태그 | 의미 |
|---|---|
| 정상 | 판정 근거가 명확한 상품 |
| 복잡 | 여러 법령 축이 동시에 해당하는 상품 |
| 애매 | 표기 불일치·외국어 원문처럼 판단이 어려운 상품 |
| 기존 실패 | 이전에 모델이 잘못 확정한 상품 |
| 처음 보는 상품·확인용 | 프롬프트 수정에 사용하지 않고 측정에만 사용하는 상품 |
| 재현용 | 오류를 발견한 페이지로, 해당 오류를 막는 규칙을 만들 때 참고한 상품 |

- 이 밖의 태그는 해당 상품이 다루는 축(식품접촉, 의료표방, 인증표기 등)과 출처(AliExpress, 쿠팡 등)를 나타낸다.
- **기존 실패는 발견될 때마다 픽스처와 정답표로 추가한다.** 같은 실패의 재발을 막는 것이 이 평가의 목적이다.
- 확인용·처음 보는 상품 정답표는 프롬프트 예시로 사용하지 않는다. 이 상품들에서 찾은 문제를 수정한 결과는 또 다른 새 상품으로 측정한다.
- 확정 전 정답표 초안은 `tests/fixtures/_raw/truth_drafts/`(git 추적 제외)에 두고 `--truth-dir`로 지정하여 측정한다. 재채점 시에는 결과 파일에 기록된 `truth_dir`을 사용한다.
- `tests/eval_truth/`에 정답표가 없는 픽스처는 채점하지 않는다. 정답 작성에는 사람의 시간이 소요되므로, 먼저 전체를 실행하여 불안정한 필드를 찾고 그 필드부터 정답을 매기는 순서가 효율적이다.

## 5. 평가 지표

### 5.1 정확도 계열 (1회 실행 기준)

```
필드 정확도   = 정답 필드 수 / 전체 필드 수
C1 치명 오류율 = C1 / 전체        ← 핵심 지표, 목표 0
C2 미탐률     = C2 / 전체
C3 오탐률     = C3 / 전체
```

### 5.2 안정성 계열 (N회 반복 기준)

같은 상품을 N회 실행하여 필드마다 분류한다.

| 분류 | 정의 | 의미 | 대응 |
|---|---|---|---|
| **안정 정답** | N회 모두 정답 | 신뢰 가능 | — |
| **안정 오답** | N회 모두 **같은** 오답 | **체계적 오류.** 프롬프트·스키마로 수정할 수 있다 | 반드시 이슈로 등록 |
| **불안정** | 실행마다 값이 다름 | 모델에 근거가 없다 | `null`이거나 `conflicts`여야 할 자리 |

값이 갈리면 등급이 우연히 같아도 불안정으로 분류한다. 예를 들어 정답이 `null`인데 예측이 true와 false를 오가면 둘 다 C1이지만 안정 오답이 아니라 불안정이다.

```
안정 정답률 = 안정 정답 필드 / 전체
안정 오답률 = 안정 오답 필드 / 전체   ← "일관되게 잘못 해석"의 직접 측정값
불안정률   = 불안정 필드 / 전체
```

**안정 오답이 불안정보다 우선순위가 높다.** 불안정은 눈에 띄지만, 안정 오답은 몇 번을 실행하여도
같은 답이 나와 "잘 되는 것처럼" 보이며, 정답표와 대조하기 전에는 발견되지 않는다.

### 5.3 진동 심각도

불안정 필드를 진동 유형으로 다시 나눈다.

| 유형 | 예 | 심각도 |
|---|---|---|
| `true ↔ false` | `wireless_charging: True→False→True` | **높음** — 정반대 확정을 번갈아 주장 |
| `true/false ↔ null` | `skin_contact: True→None→None` | 낮음 — 확신이 없다는 신호라도 남는다 |

`true ↔ false` 진동은 불안정률과 별도로 집계한다. "모르겠다"가 아니라 "모르면서 확신한다"이기 때문이다.

### 5.4 합격 기준

| 조건 | 판정 |
|---|---|
| C1이 1건이라도 발생 | **실패** — 원인 분석 없이 넘어가지 않는다 |
| 안정 오답 1건 이상 | **실패** — 수정할 수 있는 오류이므로 반드시 처리 |
| `true↔false` 진동 1건 이상 | **경고** — 해당 필드의 프롬프트 설명을 재검토 |
| 불안정률 > 10% | **경고** |

## 6. 실행

```bash
python -m app.eval.runner --all --runs 5          # 전체 실행 + 채점
python -m app.eval.runner --fixture power_bank --runs 3
python -m app.eval.runner --rescore logs/eval/<시각>.json
```

| 옵션 | 내용 |
|---|---|
| `--fixture` | 정답표 이름(확장자 제외). 여러 번 지정 가능 |
| `--all` | 정답표가 있는 픽스처 전부 |
| `--runs` | 픽스처당 실행 횟수(기본 5) |
| `--rescore` | 저장된 실행 결과를 모델 호출 없이 재채점 |
| `--truth-dir` | 정답표 폴더(기본 `tests/eval_truth`). 확정 전 초안으로 측정할 때 지정 |
| `--raw-dir` | 원문 폴더(기본 `tests/fixtures/_raw`). 임시 워크트리에서 저장소 밖 원문을 사용할 때 지정 |

- 실행 횟수는 기본 5회이다. 3회로는 2:1 다수결이 우연일 수 있고, 5회이면 "5회 모두 동일"을 안정·불안정 판정에 사용할 수 있다. 한 라운드의 안정 오답이 다음 라운드에서도 같은지 확인하면 체계적 오류임을 확정할 수 있다.
- 실패한 회차도 결과의 하나로 저장하므로 "5회 중 1회 실패"를 집계할 수 있다.
- 결과 파일과 측정 조건(`meta`)은 [EVAL_COMMON.md](EVAL_COMMON.md) 2·3장을 따른다. 추출 결과 파일에는 사용한 정답표 폴더(`truth_dir`)도 기록한다.

| 파일 | 역할 |
|---|---|
| `app/eval/grading.py` | 필드 하나를 채점하는 규칙. 모델을 호출하지 않는 순수 함수 |
| `app/eval/scoring.py` | 정답표 + N회 실행 결과 → 리포트 |
| `app/eval/runner.py` | 실행·저장·채점 CLI |
| `tests/eval_truth/*.json` | 정답표 |
| `tests/eval/test_grading.py` | 채점 규칙 검증 (모델 호출 없음) |
| `tests/eval/test_scoring.py` | 집계 로직 검증 (모델 호출 없음) |
| `tests/eval/test_truth_files.py` | 커밋된 정답표가 스키마와 일치하는지 검사 |
| `tests/eval/test_runner.py` | 원문이 없을 때의 안내 검증 |

채점 기준이 틀리면 그 기준으로 측정한 수치 전부가 무의미해지므로, `grading.py`·`scoring.py`는 모델을 호출하지 않는 결정적 테스트로 검증하며 CI에서 실행된다.
