# 추출 에이전트 검증 기준과 테스트 설계

추출 에이전트(`app/agents/extraction.py`)가 상세페이지를 **일관되게 잘못 해석하는 경우**를
찾아내기 위한 기준이다. 선택·검증 에이전트가 완성되면 같은 틀을 통합 테스트로 넓힌다.

---

## 0. 먼저 재본 결과 — 기준선

설계만 적어두면 검증이 안 되므로 채점기까지 만들어 실제로 돌렸다.

| 측정 조건 | |
|---|---|
| 코드 | `develop` @ `04edc62` |
| 모델 | `openai/gpt-4.1-mini`, `temperature=0` |
| 실행 | 픽스처 3개 × 5회 × 2라운드 = 30콜 |

**코드 버전을 함께 적는 이유**: 추출 로직이나 프롬프트가 바뀌면 이 숫자와
비교하면 안 된다. 6.1절에서 로그에 프롬프트 버전을 넣어달라고 요청한 것과 같은 이유다.
열려 있는 PR 4건(#55·#90·#92·#100)을 전부 합친 상태에서도 위 오류가 재현되는 것을
확인했다(픽스처 2개 × 2회로 확인. 규칙 레이어만 바뀌어 LLM 판단에는 영향이 없었다).

| 지표 | 값 |
|---|---|
| **C1 치명 오류율** | **24.6%** (15/61) |
| C2 미탐률 | 6.6% (4/61) |
| C3 오탐률 | 0.0% (0/61) |
| 안정 정답률 | 68.9% (42/61) |
| **안정 오답률(체계적 오류)** | **19.7%** (12/61) |
| 불안정률 | 11.5% (7/61) |
| 확정끼리 진동(true↔false) | 1건 |

### 측정 이력

프롬프트나 추출 로직이 바뀌면 위 수치와 비교하면 안 된다. 무엇을 왜 바꿨는지 여기에
한 줄씩 남기고, 실행 기록에는 프롬프트 지문이 자동으로 들어간다(5절).

| 버전 | 커밋 | 프롬프트 지문 | 무엇을 왜 바꿨나 | C1 | 안정 오답 | 불안정 |
|---|---|---|---|---|---|---|
| v1 (기준선) | `04edc62` | `02889dd2ee11` | — | 24.6% | 19.7% | 11.5% |

> 지문은 `logs/eval/<타임스탬프>.json`의 `meta.prompt_sha256` 앞 12자다.
> v1은 이 기록 기능이 생기기 전 측정이라 지문을 나중에 채워 넣었다
> (기준선 이후 `extraction.md`는 바뀌지 않았고 규칙 레이어만 수정됐다).

### 두 라운드에서 똑같이 재현된 오류

5회씩 두 번, 총 10회 중 **10회 모두 같은 오답**이 나온 것들이다.
프롬프트 원칙 1은 "언급이 없다는 이유만으로 boolean 필드를 false로 채우지 않는다"고
명시하는데, 모델이 이 지시를 일관되게 어긴다.

| 픽스처 | 필드 | 정답 | 10회 결과 |
|---|---|---|---|
| ali_sample | `food_contact` | null | `false` ×10 |
| ali_sample | `wireless_comm` | null | `false` ×10 |
| ali_sample | `wireless_shield` | null | `false` ×10 |
| ali_sample | `heating` | null | `true` ×10 |
| wireless_shield_rfid | `food_contact` | null | `false` ×10 |
| wireless_shield_rfid | `skin_contact` | null | `true` ×10 |
| power_bank | `battery_included` | null | `false` ×10 |
| power_bank | `battery_is_the_product` | null | `true` ×10 |
| power_bank | `electrical_powered` | null | `true` ×10 |

power_bank 세 줄은 **페이지가 명시적으로 부정한 것을 확정한다**. 스펙표에
"전자 부품 또는 마더보드 미포함"이라고 적혀 있는데 `electrical_powered=true`,
`battery_is_the_product=true`로 답한다. 규칙 레이어가 conflicts로 모순 후보를
넘겼는데도 배터리 유무를 확정한다(#40에서 발견한 문제가 그대로 남아 있다).

### 값이 흔들리는 것도 따로 있다

| 픽스처 | 필드 | 1라운드 | 2라운드 |
|---|---|---|---|
| ali_sample | `target_age` | `['어린이용', None, '어린이용', '어린이용', None]` | `[None, '어린이용', '어린이용', None, None]` |
| ali_sample | `wireless_charging` | `[True, False, False, False, False]` | `[False, False, False, False, True]` |
| power_bank | `skin_contact` | `[None, True, None, None, None]` | `[None, True, None, True, None]` |

`wireless_charging`은 `true`와 `false`를 오간다. "모르겠다"가 아니라
**모르면서 정반대 확정을 번갈아 주장**하는 것이라 따로 센다.

### 이 결과가 설계에 주는 세 가지 제약

1. **한 번 돌려서 채점하면 안 된다.** 다음 실행에서 다른 답이 나온다.
2. **"정확도" 하나로는 부족하다.** True/False를 오가는 필드는 정확도 67%가 아니라 "근거가 없다"는 뜻이다.
3. **`None`과 `False`를 같은 오답으로 세면 안 된다.** `False`는 "없음을 확인"이라는 적극적 주장이고,
   `None`은 "모르겠다"는 유보다. 규제 판정에서 두 값의 위험도는 전혀 다르다.

## 1. 각 attribute의 정답·오답 판정 기준

22개 필드를 채점 방식이 다른 3군으로 나눈다.

### 1.1 3-state boolean 15개 — 위험도 차등 채점

대상: `electrical_powered` `wireless_comm` `wireless_charging` `wireless_shield`
`battery_included` `battery_is_the_product` `heating` `food_contact` `skin_contact`
`medical_claim` `cosmetic_claim` `weapon_like` `plant_material` `chemical_product` `for_children`

정답(GT)과 예측(P)의 조합 9가지를 **같은 무게로 세지 않는다.**

| GT \ 예측 | `true` | `false` | `null` |
|---|---|---|---|
| **`true`** | 정답 | 🔴 **C1** | 🟡 C2 |
| **`false`** | 🟠 C3 | 정답 | 🟡 C2 |
| **`null`** | 🔴 **C1** | 🔴 **C1** | 정답 |

**🔴 C1 (치명) — 규제 판정이 조용히 틀어진다**
- `GT=true, P=false`: 해당 특성을 "없음"으로 확정 → 심사 툴이 선택되지 않음 → 규제 미검출
- `GT=null, P=true/false`: 페이지에 근거가 없는데 확정 → 하위 에이전트가 그 확정을 신뢰

**🟡 C2 (보수적 미탐) — 안전한 실패**
- `P=null`: 정보 부족으로 넘어감 → 하위에서 "확인 필요"로 처리 가능

**🟠 C3 (오탐) — 비용만 드는 실패**
- `GT=false, P=true`: 불필요한 툴이 실행됨. 판정 자체는 틀리지 않는다

> C1을 0으로 만드는 것이 1차 목표다. C2·C3은 감시하되 C1과 바꿔치기할 수 있으면 바꾼다
> (확정할 수 없으면 `null`로 두는 편이 항상 낫다).

**GT를 `null`로 매기는 기준**: 상세페이지 텍스트·이미지에 그 특성을 판단할 **직접 근거가 없을 때**다.
"케이스니까 손에 닿겠지" 같은 상식 추론은 근거가 아니다. 추론으로 채우기 시작하면
정답 자체가 사람마다 달라져서 기준이 무너진다.

### 1.2 자유 텍스트 4개 — 완전 일치로 채점하지 않는다

실측에서 `intended_use`가 매번 다르게 나왔다(`"가정용 실내 오래 지속되는 향기 디퓨저 스틱"` vs
`"가정용 실내 향기 디퓨저"`). 의미는 같은데 표현이 다르므로 문자열 비교는 무의미하다.

| 필드 | 채점 방식 | 이유 |
|---|---|---|
| `target_age` | **원문 부분 문자열 포함** 여부 | 프롬프트가 원문 보존을 요구한다. `"만 14세 이상"`을 `"14세"`로 줄이면 오답 |
| `product_name` | 정답에 등록한 **필수 키워드 전부 포함** | 제목이 길어 표현이 흔들린다. 핵심 명사만 본다 |
| `category` | **허용 목록 중 하나** | `"방향제"` / `"디퓨저"` 같은 동의어를 미리 등록 |
| `intended_use` | **필수 키워드 포함** | 위와 같음 |

`target_age`만 엄격하게 보는 이유: 이 필드는 값 자체가 판정 근거로 쓰인다(어린이제품
안전 기준). 나머지는 툴 선택 참고용이라 표현 흔들림을 허용한다.

### 1.3 리스트 3개 — 놓친 것과 지어낸 것을 나눠 센다

| 필드 | 필수(놓치면 오답) | 금지(있으면 오답) | 중점 |
|---|---|---|---|
| `attributes` | 정답에 등록한 **값** 전부 (항목 이름은 안 봄) | 페이지에 없는 값 | 재현율·정밀도 둘 다 |
| `conflicts` | 정답에 등록한 모순 전부 | — | **재현율만** |
| `listing_text` | 정답에 등록한 문구 포함 | — | 재현율만 |

`conflicts`의 오탐을 세지 않는 이유: #40 리뷰에서 합의한 대로 모순은 "확정"이 아니라
"확인이 필요한 후보"다. 오탐 비용은 사람이 한 줄 더 읽는 것이고, 미탐 비용은 전안법·전지
축 라우팅이 통째로 빠지는 것이다.

## 2. 정답과 근거를 기록하는 형식

정답 파일은 픽스처와 같은 이름으로 둔다. 러너와 테스트가 그대로 읽어서 채점한다.

```
ai/tests/eval_truth/<픽스처 이름>.json
```

채점 방식이 다른 세 묶음(`booleans` / `verbatim` / `keywords`)으로 나눠 적는다.
아래는 실제로 쓰고 있는 `power_bank.json`에서 발췌한 것이다.

```json
{
  "fixture": "power_bank.txt",
  "reviewed_by": "gityhb",
  "reviewed_at": "2026-09-16",
  "tags": ["기존 실패", "애매"],
  "summary": "제목엔 'MagSafe 1460mAh 케이스', 스펙표엔 '배터리 미포함'. 어느 쪽도 확정할 수 없다.",

  "booleans": {
    "battery_included": {
      "value": null,
      "evidence": "제목 'MagSafe 1460mAh 케이스' / 스펙표 '배터리 속성: 배터리 미포함'",
      "why_not_other": "두 표기가 정면으로 충돌한다. true도 false도 확정 근거가 없고 conflicts로 보고해야 한다."
    },
    "plant_material": {
      "value": false,
      "evidence": "스펙표 '본체재질: TPU(열가소성 폴리우레탄)'",
      "why_not_other": "재질이 명시돼 있고 식물성이 아니다."
    },
    "skin_contact": {
      "value": null,
      "evidence": "(피부 접촉 관련 언급 없음)",
      "why_not_other": "'휴대폰 케이스니까 손에 닿는다'는 상식 추론이다. 페이지에 근거가 없다."
    }
  },

  "verbatim": {
    "target_age": { "value": null, "evidence": "(연령 표기 없음)" }
  },

  "keywords": {
    "product_name": { "required": ["케이스"] },
    "category": { "allowed": ["보조배터리", "휴대폰 액세서리", "휴대폰 케이스"] }
  },

  "attributes_required": [
    { "name": "배터리 용량", "value": "1460mAh", "evidence": "제목 'MagSafe 1460mAh 케이스'" }
  ],
  "attributes_forbidden": [
    { "name": "정격전압", "value": "220V", "reason": "페이지에 전압 표기가 전혀 없다" }
  ],
  "conflicts_required": [
    { "must_contain": "1460mAh", "evidence": "용량 표기와 '배터리 미포함'이 같은 페이지에 있다" }
  ]
}
```

`attributes`는 **값으로만 대조하고 항목 이름은 보지 않는다.** 실측에서 같은 용량을
런에 따라 `"용량"`과 `"배터리 용량"`으로 번갈아 적었고, 인증 마크 두 개를
`"CE-RoHS; CE-EMC(Electric)"` 한 항목에 이어 쓰기도 했다. 이름·묶음이 다르다는
이유로 "놓쳤다"고 세면 사실 포착 여부가 아니라 라벨 표현을 재게 된다.

### `why_not_other`를 필수로 두는 이유

`null`과 `false`를 가르는 판단이 이 설계에서 가장 자주 틀리는 지점이다(실측에서 모델이
15개 중 14개를 `false`로 확정한 것이 바로 그 실패다). 정답을 매긴 사람이 **왜 다른 값이 아닌지**를
남기지 않으면:

- 나중에 다른 사람이 그 정답에 동의하는지 검증할 수 없다
- 모델이 틀렸을 때 프롬프트를 어떻게 고쳐야 하는지 단서가 없다
- 정답 자체가 틀렸을 가능성을 걸러낼 수 없다

`evidence`는 **원문 인용**으로 적는다. 요약하면 나중에 원문과 대조가 안 된다.

## 3. 테스트 상품 선정

현재 픽스처 12개를 요청하신 4분류로 매핑하면 이렇다.

| 분류 | 픽스처 | 무엇을 보는가 |
|---|---|---|
| **정상** | `ali_sample` (무선 헤어드라이어) | 전기·발열·피부접촉·어린이가 명확 |
| | `plant_material_basket` (대나무 바구니) | 식물성 소재 단일 축 |
| | `heating_device_no_claim` (온열 제품) | 발열은 있으나 의료 표방 없음 |
| | `wireless_shield_rfid` (RFID 차단 지갑) | 차폐 ≠ 통신 구분 |
| **복잡** (여러 축 동시) | `kc_certified_fan` (KC 인증 선풍기) | 전기 + 전파 + 배터리 + 인증번호 2종 |
| | `toy_weapon_shaped` (장난감 총) | 완구 + 전기 + 무기 형태 + 어린이 |
| | `wireless_charging_pad` | 전기 + 전파 + 무선충전 3종 구분 |
| **애매** | `age_label_vs_target_mismatch` | 표기 연령과 광고 대상이 불일치 |
| | `chinese_material_labels` (중국어) | 원문 언어가 한국어가 아님 |
| | `chinese_squishy_1.png` (이미지) | 텍스트 없이 이미지만 |
| **기존 실패** | `power_bank` | 제목/스펙표 모순을 LLM이 못 잡고 `false`로 확정했던 케이스 |
| | `chemical_product_diffuser` | 카테고리("디퓨저")와 속성("무향") 충돌을 카테고리 쪽으로 확정했던 케이스 |

### 아직 없어서 채워야 하는 축

여섯 개 법령 축 중 커버가 비어 있는 것:

- **식품 접촉** (`food_contact=true`인 상품) — 식품용 기구·용기 축이 통째로 미검증
- **의료·화장품 표방** (`medical_claim` / `cosmetic_claim=true`) — 표시광고 축의 핵심인데
  정답표를 쓴 3건은 모두 `false`이고, 나머지 픽스처는 아직 정답을 매기지 않았다.
  "혈액순환 개선" 같은 효능 문구가 실제로 있는 샘플이 필요하다.
  (`heating_device_no_claim`에 "전문 의료용품"이 나오지만 판매자 스토어 분류이지
  제품 효능 표방이 아니다. 이런 문구를 모델이 어떻게 읽는지도 정답을 매겨 확인할 가치가 있다)
- **전지 자체가 상품** (`battery_is_the_product=true`) — 진짜 보조배터리.
  `power_bank`는 이름과 달리 케이스다
- **인증번호 형식 변종** — `kc_certified_fan` 한 건뿐이라 발급 시기별 자릿수 변종이 미검증

정상 4 : 복잡 3 : 애매 3 : 기존 실패 2 비율은 유지하되, 위 4개 축을 채우면 15건 정도가 된다.
**기존 실패는 발견될 때마다 반드시 픽스처로 추가한다** — 같은 실패가 다시 나는 것을
막는 게 이 테스트의 존재 이유다.

## 4. 평가 지표

### 4.1 정확도 계열 (1회 실행 기준)

```
필드 정확도   = 정답 필드 수 / 전체 필드 수
C1 치명 오류율 = C1 / 전체        ← 핵심 지표, 목표 0
C2 미탐률     = C2 / 전체
C3 오탐률     = C3 / 전체
```

### 4.2 안정성 계열 (N회 반복 기준) — 멘토 피드백에 직접 대응

같은 상품을 N회 돌려서 필드마다 분류한다.

| 분류 | 정의 | 의미 | 대응 |
|---|---|---|---|
| **안정 정답** | N회 모두 정답 | 신뢰 가능 | — |
| **🔴 안정 오답** | N회 모두 **같은** 오답 | **체계적 오류.** 프롬프트·스키마로 고칠 수 있다 | 반드시 티켓화 |
| **🟠 불안정** | 런마다 값이 갈림 | 모델에 근거가 없다 | `null`이거나 `conflicts`여야 할 자리 |

```
안정 정답률 = 안정 정답 필드 / 전체
안정 오답률 = 안정 오답 필드 / 전체   ← "일관되게 잘못 해석"의 직접 측정값
불안정률   = 불안정 필드 / 전체
```

**안정 오답이 불안정보다 우선순위가 높다.** 불안정은 눈에 띄지만, 안정 오답은 몇 번을 돌려도
같은 답이 나와서 "잘 되는 것처럼" 보인다. 정답표와 대조하기 전에는 발견되지 않는다.

### 4.3 진동 심각도

불안정 필드를 진동 유형으로 다시 나눈다.

| 유형 | 예 (실측) | 심각도 |
|---|---|---|
| `true ↔ false` | `wireless_charging: True→False→True` | **높음** — 정반대 확정을 번갈아 주장 |
| `true/false ↔ null` | `skin_contact: True→None→None` | 낮음 — 확신이 없다는 신호라도 남는다 |

`true ↔ false` 진동은 불안정률과 별도로 집계한다. 이건 "모르겠다"가 아니라
"모르면서 확신한다"이기 때문이다.

### 4.4 합격 기준 (초안)

| 조건 | 판정 |
|---|---|
| C1이 1건이라도 발생 | **실패** — 원인 분석 없이 넘어가지 않는다 |
| 안정 오답 1건 이상 | **실패** — 고칠 수 있는 오류이므로 반드시 처리 |
| `true↔false` 진동 1건 이상 | **경고** — 해당 필드의 프롬프트 설명을 재검토 |
| 불안정률 > 10% | **경고** |

수치는 첫 측정 후 조정한다. 지금은 기준선 자체가 없다.

## 5. 반복 실행 테스트 방식

### 실행 횟수: N = 5 (라운드 2회 = 10회)

- 3회로는 2:1 다수결이 우연일 수 있어 부족하다
- 5회면 "5회 모두 동일"을 안정/불안정 판정에 쓸 수 있다
- 기준선은 **5회를 두 라운드** 돌려 잡았다. 한 라운드에서 안정 오답으로 잡힌 것이
  다음 라운드에서도 같은지 봐야 "체계적 오류"라고 말할 수 있다
- 비용: 픽스처 15건 × 5회 = 75콜. `gpt-4.1-mini` 기준 부담 없는 수준

### 구현

| 파일 | 역할 |
|---|---|
| `app/eval/grading.py` | 필드 하나를 채점하는 규칙. LLM을 부르지 않는 순수 함수 |
| `app/eval/scoring.py` | 정답표 + N회 실행 결과 → 리포트 |
| `app/eval/runner.py` | 실행·저장·채점 CLI |
| `tests/eval_truth/*.json` | 정답표 |
| `tests/test_eval_grading.py` | 채점 규칙 검증 (LLM 없음) |
| `tests/test_eval_scoring.py` | 집계 로직 검증 (LLM 없음) |
| `tests/test_eval_truth_files.py` | 커밋된 정답표가 스키마와 맞는지 검사 |
| `tests/test_eval_runner.py` | 원문이 없을 때의 안내 검증 |

```bash
python -m app.eval.runner --all --runs 5          # 전체 실행 + 채점
python -m app.eval.runner --fixture power_bank --runs 3
python -m app.eval.runner --rescore logs/eval/20260916-014923.json
```

### 실행 결과를 항상 파일로 남긴다

`logs/eval/<타임스탬프>.json`에 각 런의 `Product`를 그대로 저장한다.
채점 기준을 고쳤을 때 **LLM을 다시 부르지 않고 같은 데이터로 재채점**할 수 있어야
기준을 마음 놓고 다듬을 수 있다.

실제로 이 기능이 바로 쓰였다. 첫 채점에서 `attributes`를 `(이름, 값)` 정확 일치로
봤더니 인증 마크 2건이 "누락"으로 잡혔는데, 저장된 원본을 보니 모델이
`"CE-RoHS; CE-EMC(Electric)"` 한 항목에 담은 것이었다. 채점기를 값 기준으로 고치고
**API 재호출 없이** 재채점해서 오탐을 걷어냈다.

### 무엇으로 쟀는지 함께 남긴다

결과 파일 맨 앞에 `meta`가 붙는다.

```json
{
  "meta": {
    "run_at": "2026-09-21T10:35:53Z",
    "git_commit": "eefecaa",
    "git_dirty": false,
    "model": "openai/gpt-4.1-mini",
    "prompt_path": "app/prompts/extraction.md",
    "prompt_sha256": "02889dd2ee11ed337c94102505c1c5bca3c00e2cf468c9f0fc06a4f2f820c77f",
    "runs": 5
  },
  "results": { ... }
}
```

**프롬프트 지문이 핵심이다.** 사람이 버전을 적는 방식은 까먹지만 파일 해시는 틀리지 않는다.
`--rescore`로 예전 결과를 다시 채점할 때 지금 프롬프트와 지문이 다르면 경고한다.
비교하면 안 되는 두 측정치를 나란히 놓는 것이 이 평가에서 제일 흔한 사고다.

```
[주의] 지금과 다른 프롬프트로 나온 결과입니다 (기록 02889dd2ee11 / 현재 7b1c9f04a2de).
       같은 기준선으로 비교하면 안 됩니다.
```

`git_commit`만으로는 부족해서 `git_dirty`도 같이 적는다. 커밋하지 않은 수정이 있으면
그 해시의 코드로 잰 값이 아니다. 줄바꿈(CRLF/LF) 차이는 지문에 영향을 주지 않으므로
윈도우에서 잰 값과 CI에서 잰 값이 같은 프롬프트로 인식된다.

### 채점기 자체를 먼저 테스트한다

채점 기준이 틀리면 그걸로 잰 수치 전부가 무의미해진다. 그래서 `grading.py`·`scoring.py`는
LLM 없이 도는 결정적 테스트로 덮었다(현재 53건). CI에서 그대로 돈다.

LLM을 실제로 부르는 평가는 CLI로만 돌린다. 확률적이라 CI 통과/실패 기준으로 쓸 수 없고,
**기준선 대비 비교**로 봐야 하기 때문이다.

### 정답표가 없는 픽스처

`eval_truth/` 파일이 없으면 채점하지 않는다. 정답을 매기는 데 사람 시간이 드니,
먼저 전체를 돌려 불안정 필드를 찾고 그 필드부터 정답을 매기는 순서가 효율적이다.

## 6. 파이프라인 쪽에 요청드리는 로그·출력

통합 테스트로 확장할 때 필요한 것들입니다. 지금 추출 단계에 없는 것도 포함했습니다.

### 6.1 로그 — `app/usage.py`가 이미 대부분 해결한다

검증 에이전트 PR로 들어온 `app/usage.py`가 호출 1건씩 JSONL로 기록하고 있다.
이 평가 러너도 여기에 붙였다(`record("extraction-eval", ...)`).

| 항목 | 상태 |
|---|---|
| 상품 식별자 | ✅ `subject_id` |
| 요청 모델 / 실제 응답 모델 | ✅ `configured_model` / `reported_model` |
| 토큰 사용량 · 캐시 적중분 | ✅ |
| 예상 비용(원) | ✅ `estimated_cost_krw` |
| 성공 여부 · 소요 시간 · 오류 타입 | ✅ `success` / `latency_ms` / `error_type` |
| **프롬프트 버전** | ❌ 없음 |
| **실행 회차(run_id)** | ❌ 없음 |

남은 두 개만 채워주시면 좋겠습니다.

- **프롬프트 버전**: 프롬프트가 바뀌면 과거 측정치와 비교하면 안 된다. 지금은
  기준선을 다시 잰 것인지 프롬프트가 바뀐 것인지 로그로 구분할 수 없다.
  프롬프트 파일 해시 한 줄이면 충분하다.
- **실행 회차**: 같은 상품을 N회 돌릴 때 회차를 구분해야 안정성 집계를 로그만으로
  재현할 수 있다. 지금은 평가 러너가 `subject_id`에 인덱스를 붙여 우회하고 있다.

**추출 에이전트도 `usage.py`에 붙였다.** 예전에는 자체 `_log_token_usage`로 로그에만 남겨서
평가로 쓴 토큰과 비용이 집계에서 통째로 빠져 있었다(평가 러너는 사용량 자리에 `None`을
넘기고 있었다). 이제 호출 1건마다 실제 사용량이 기록된다.

평가로 쓴 비용과 운영으로 쓴 비용은 이름을 나눠 쌓는다. 평가 러너는 에이전트를
`usage_agent="extraction-eval"`로 만들고, 파이프라인에서 쓸 때는 기본값인 `"extraction"`이
된다. 섞이면 어느 쪽이 얼마인지 볼 수 없다.

**프롬프트 버전은 평가 결과 파일의 `meta`로 해결했다**(5절). `usage.jsonl`은 호출 단위인데
프롬프트는 실행 단위라 실행 기록에 두는 편이 맞다고 봤다. 운영 파이프라인에서도 필요하면
그때 따로 논의하면 좋겠다.

붙이고 나서 바로 보인 것이 하나 있다. **`cached_input_tokens`가 0이다.**

```
input_tokens        4555
cached_input_tokens 0      <- 고정 prefix가 캐시에 안 걸리고 있다
output_tokens       1862
estimated_cost_krw  7.3
```

시스템 프롬프트와 스키마가 호출마다 같으므로 캐시가 걸리면 이 값이 잡혀야 한다. 지금은
매번 전체 입력 단가를 내고 있다는 뜻이다. 게이트웨이가 캐시를 지원하는지부터 확인해야 해서
이번 범위에는 넣지 않았다. **측정을 붙이지 않았으면 몰랐을 항목이다.**

### 6.2 중간 산출물 덤프

각 에이전트 경계에서 JSON을 그대로 남겨주시면 좋겠습니다.

```
추출 → Product
선택 → SelectionResult (선택 내역 + 실제 실행 이력)
종합 → DraftAssessment
검증 → VerificationResult
```

통합 테스트로 넓힐 때 **어느 단계에서 틀렸는지** 가르려면 이게 필요합니다.
최종 판정만 보면 추출이 틀린 건지 선택이 틀린 건지 알 수 없습니다.

### 6.3 실패했을 때

`ExtractionFailedError`처럼 단계별 예외를 유지하고, 원인 예외를 `__cause__`에 보존해주세요.
N회 반복 중 일부만 실패하는 경우가 있어서, **실패도 런 결과의 하나로 기록**해야
"5회 중 1회 실패"를 집계할 수 있습니다.

### 6번을 어떻게 할지 — 팀 결정이 필요한 지점

기준선에서 나온 안정 오답 대부분이 하나의 패턴이다. **프롬프트는 "언급이 없으면
비워 두라"고 하는데 모델은 `false`(또는 `true`)로 확정한다.**

여기엔 두 가지 읽기가 있고, 어느 쪽을 택하느냐에 따라 고칠 대상이 달라진다.

1. **모델이 지시를 어긴 것** → 프롬프트를 강화하거나 스키마로 강제한다.
   (예: `false`를 쓰려면 근거 문장을 같이 내게 하는 필드 추가)
2. **정답 기준이 과하게 엄격한 것** → 세상 지식으로 확정 가능한 것은 `false`를 허용한다.
   (헤어드라이어가 음식에 닿지 않는다는 건 페이지에 없어도 사실이다)

지금 정답표는 1번을 전제로 쓰였다. **프롬프트에 그렇게 적혀 있기 때문**이지
내 취향이 아니다. 다만 2번이 팀 결론이라면 프롬프트 원칙 1과 정답표를 함께 바꿔야 한다.

규제 판정 관점에서는 1번이 안전하다. 근거 없는 `false`는 심사 툴을 통째로
건너뛰게 만들고, 그건 조용히 일어난다. 선택 에이전트 프롬프트도 이미
"None은 '없다'가 아니다"를 원칙으로 두고 있어 방향이 맞는다.
